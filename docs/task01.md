# Task 01 — Minimal Test Triage Workflow

## 背景

你需要实现一个基于 LangGraph 的最小测试判定模块。

上游系统已经完成了：

* 测试用例自然语言解析
* 测试数据包解析
* 行为信息提取

因此本任务接收到的输入已经是结构化数据，不需要处理自然语言理解、日志解析或知识库查询。

---

## 输入

一次测试样本包含两部分：

### Test Spec

描述测试设计，至少包含：

* 故障类型
* 期望车辆行为

### Observation

描述测试实际观测结果，至少包含：

* 实际车辆行为
* 数据是否完整

车辆行为使用有限的结构化枚举表示，不使用自由自然语言作为判定依据。

---

## 业务规则

系统需要输出以下三种 Triage 结果之一：

### PASS

输入数据合法且完整，并且实际行为与期望行为一致。

### FAIL

输入数据合法且完整，但实际行为与期望行为不一致。

### RETEST

输入数据缺失、非法或不完整，无法进行可靠判定。

系统必须提供能够解释判定结果的原因。

---

## 功能要求

使用 LangGraph 实现该流程。

系统至少应完成：

1. 输入完整性与合法性校验。
2. 对合法输入执行确定性的 Triage 判断。
3. 对非法或不完整输入返回 RETEST。
4. 生成结构化最终结果。
5. 提供便于用户阅读的结果描述。
6. 能够在运行时观察 Graph 的节点执行过程和 State 更新。

---

## 输出

最终对外结果至少包含：

* `triage_res`
* `reason`
* `friendly_content`

最终输出必须是结构化数据。

---

## 约束

* 必须使用 LangGraph。
* 当前任务不允许使用 LLM。
* 当前任务不允许使用 Tool Calling。
* 不使用 RAG、MCP、数据库或外部服务。
* 不实现 Agentic Loop。
* 不实现 Checkpoint / Persistence。
* 不接入 LangSmith。
* 不为了未来需求提前增加无关抽象。
* 业务状态与执行追踪信息应保持合理的职责边界。

---

## 验收场景

至少验证以下三类输入：

### Case 1

输入合法、数据完整、实际行为符合期望。

预期：
`PASS`

### Case 2

输入合法、数据完整、实际行为不符合期望。

预期：
`FAIL`

### Case 3

输入缺失、字段非法或数据不完整。

预期：
`RETEST`

---

## 交付要求

完成后应能够：

1. 运行程序并得到正确结果。
2. 展示 Graph 的实际执行过程。
3. 解释 State、Node、Edge 和 Graph 的设计。
4. 解释为什么采用当前节点划分。
5. 说明输入、内部 State 和最终输出之间的职责区别。
6. 证明三个核心验收场景均已实际执行验证。

不要求前端界面。
